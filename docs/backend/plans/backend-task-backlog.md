# 后续任务池 / Backlog

## 说明

这个文件用于记录当前不做、但后续不应该忘记的事项。

第 5–9 天优先做业务功能闭环，以下内容先放入任务池，等基础功能稳定后再排期。

## 使用规则

1. 每次准备新阶段计划时，先阅读本文件。
2. 从任务池中挑选与当前目标最相关的任务。
3. 移入正式计划前，必须重新确认范围和验收标准。
4. 不允许无边界地把所有任务一起做。
5. 已经排进计划的条目，在「适合阶段」或「说明」里标注去处，**不要直接删行**——删掉之后，看历史的人分不清是做完了还是被遗漏了。

## 一、工程优化

| 优先级 | 任务 | 说明 | 适合阶段 |
| --- | --- | --- | --- |
| P1 | 全局错误处理器 | 统一处理 404、405、500，返回统一 JSON | 功能闭环后 |
| P1 | 统一分页工具 | 统一 `page`、`page_size`、`offset` 校验和计算 | **已排期：第 6 天第 1 个任务** |
| P1 | 统一序列化工具 | 把博主、基金、持仓、操作记录的序列化逻辑集中 | 接口增多后 |
| P1 | repository / service 分层 | route 只负责协议，service 负责业务，repository 负责数据库 | 业务模块稳定后 |
| P1 | 数据库索引与约束巡检 | 检查唯一索引、外键、查询索引是否合理 | 数据量增加前 |
| P1 | 金额与份额统一用 `Decimal` | 现在 `operations` 接口层用 `float()` 转换，数据库是 `DECIMAL`。单条记录没问题，但做收益汇总要累加几十笔金额，`float` 下 `0.1 + 0.2 != 0.3`，总成本会对不上账 | **第 8 天做收益计算前必须完成**，否则收益数字不可信 |

| P2 | pytest 覆盖率检查 | 输出覆盖率报告，找出明显未测模块 | 自动化测试稳定后 |
| P2 | 数据备份与恢复脚本 | 提供最低限度的 MySQL 备份和恢复能力 | 有真实数据后 |
| P2 | 环境配置拆分 | 区分开发、测试、部署环境 | 准备部署前 |

| P2 | 部署验收与回滚文档 | 明确部署检查步骤和失败回滚方式 | 部署阶段 |
| P3 | Docker 化 | 固定开发/部署环境 | 项目结构稳定后 |
| P3 | CI/CD | 提交后自动测试、构建、部署 | 团队协作或频繁发布时 |

## 二、业务功能增强

| 优先级 | 任务 | 说明 |
| --- | --- | --- |
| P1 | 持仓快照持久化 | 当前第一版实时计算，后续可以按日期落库，提高查询性能 |
| P1 | 操作记录编辑接口 | 删除已在任务 022 实现（`DELETE /api/v1/operations/{id}`），录错的记录先删除再重新录入。**编辑（PUT）仍在池中**：要先决定是否允许修改历史操作，以及修改后如何重算快照 |
| P1 | 基金详情接口 | `GET /api/v1/funds/{fund_id}`。博主和初始持仓都有详情或按 ID 查询的能力，基金只有列表。前端做基金维度的收益页时会需要单只基金的完整信息 |
| P2 | 操作记录详情接口 | `GET /api/v1/operations/{id}`。第一版列表已经返回全部字段，暂时不需要 |
| P2 | 超额卖出校验 | 第一版不校验，剩余份额可以为负，由使用者自己发现录入错误。要做的话得先算出该日剩余份额，依赖持仓快照 |
| P2 | 手续费支持 | 买入、卖出时记录手续费，并影响真实成本 |
| P2 | 税费支持 | 如后续涉及境外基金或特殊产品 |
| P2 | 红利再投资 | 现金分红之外，支持分红转为份额 |
| P2 | 基金拆分 / 合并 | 处理份额和成本的复杂变化 |
| P2 | 数据导入导出 | 支持 Excel/CSV 导入博主、基金、持仓、净值、操作记录。净值 CSV 导入已排进第 6 天，其余仍在池中 |
| P2 | 数据模板下载 | 给前端提供导入模板 |
| P2 | 级联删除改回数据库层 | 现在删博主是在应用层按 `operations` → `initial_positions` → `bloggers` 顺序删（任务 022）。表多了之后这个顺序会越来越长，可以考虑改成外键 `ON DELETE CASCADE`。但那样误删一个博主会静默连带删掉全部历史记录，取舍要重新确认 |
| P3 | 定时任务 | 每日快照、每日统计、自动备份等 |
| P3 | 数据变更审计 | 记录谁在什么时候修改了什么数据 |
