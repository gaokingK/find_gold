## 四、口径不一致问题

### C1：`047` 范围说明自指错误

范围说明「不包含」一节写「看板模块三个接口的测试（**任务 047** 的范围）」——047 是收益模块接口测试，看板测试是 048、049 的范围。改成「（任务 048、049 的范围）」。顺带检查：049 的范围说明写的是「那是任务 048 的范围」，正确。

### C2：048/049 的 `assert_number` 与 046/047 两套数值比较口径

046/047 的 `assert_number` 用 `Decimal.quantize(exp, rounding=ROUND_HALF_UP)`；048/049 的同名辅助函数用 `round(actual, places)`——`round(float, n)` 是 ROUND_HALF_EVEN（银行家舍入），且 044 整节新概念在讲「为什么不能这么干」。同一批补发文档两种写法并存，等于告诉新手「两种都对」。测试场景下踩中 0.5 边界的概率低，但口径必须唯一。改法见第六节第 6 条。

### C3：`create_nav_history` 的兜底定义有三份、默认值不同

044 步骤 7：`nav="1.2345"`；047 步骤 2 兜底：`nav="1.0000"`；048 步骤 2 兜底：无默认值。正常路径下 044 先做、兜底不触发，无实害；但如果新手按「043 → 047 → 044」的顺序穿插（README 不禁止），会用 047 的版本落库，之后 044 步骤 7 又要求「追加」一次，`grep -rn "def create_" tests/` 的唯一性检查立刻失败。改法见第六节第 7 条。

### C4：README 顺序约束 3（045 → 046–049）是伪约束

见结论 3。045 的真实下游是 034–038、040 的手工验证和协调人的六份文档 ID 替换（045 文末已交代）。README 约束 3 应改写，并补上真正缺失的「044 → 046」。

### C5：047 前置条件缺 046

README 约束 4 说「046 → 047：先测 Service 层再测接口」，但 047 前置条件五条里没有 046。文档与 README 不一致，新手只读文档时不知道为什么验收要按这个顺序。补一条即可。

### C6：044 估算依据的测试数写错

估算依据写「写 9 个测试用例」，步骤 7 实际是 **7 个测试函数**（第一个函数内含 2 个场景、最后一个循环 8 个参数）。完成标准写的「新增测试不少于 7 个」是对的，只有估算依据这一处数字错了。改成「7 个测试函数（覆盖 14 组参数场景）」。
